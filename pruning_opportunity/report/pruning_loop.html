Final pruning counts · 19 November 2026 · DuckDB v1.4.4 · full scale only

Letting an AI agent tune partition statistics from what the database tells it

We instrumented DuckDB so it reports, per query, every partition it read without finding a single matching row. Those reports point at specific columns and predicates, and statistics written for exactly those recover most of the wasted reads.

This page reports the final pruning numbers at full scale only: the paper's sensor microbenchmark at 1 billion rows (unsorted data, point and range queries) and ClickBench at 100 million rows. Partitions are DuckDB row groups of 8,192 rows. Both databases were loaded with a single thread so that every partition holds exactly 8,192 rows. The page shows counts only. Execution times will follow in a separate run.

Step 1 · Observe

The telemetry: what DuckDB did with every partition

We patched an unmodified DuckDB v1.4.4 with counters that are off unless an environment variable names a log file. At the end of each query DuckDB writes one JSON line per table scan, and every partition lands in exactly one category:

CategoryMeaningWhat the agent learns
PrunedSkipped before reading, with the check that skipped it (min/max, statistic, cache, row-id range)Which predicates already work
Wasted readRead in full, but no row passed the filters pushed into the scanCould have been pruned: the opportunity, with the filters responsible
Read, with matching rowsAt least one row passedCan never be pruned; the floor for any statistic

Data loaded with one thread

A parallel load leaves some row groups short of 8,192 rows and shifts partition boundaries, which changes the counts. Both databases were therefore reloaded single-threaded. The 1B-row sensor table ran out of memory as a single load (11.5 GB resident against a 4 GB limit), so it was loaded in 11 committed chunks of 12,207 × 8,192 rows each.

  • Sensor, unsorted: 1,000,000,000 rows, 122,071 partitions, all of 8,192 rows except the last (2,560).
  • ClickBench: 99,997,497 rows, 12,207 partitions, all of 8,192 rows except the last (5,945).

Validated against plain SQL

For 20 queries per sensor setup, a plain SQL query counted the partitions (rowid // 8192) holding a matching row. The counters agree on all 80 of 80 queries. Every scan also satisfies pruned + read = total. Because a match inside a pruned partition would show up as a mismatch, this also confirms that min/max never pruned a partition with a match. For ClickBench Q20–Q22, the counted partitions with matches (3,175, 587 and 2,778) equal the plain-SQL ground truth exactly.

Step 2 · Diagnose

Where the reads are wasted

Sensor microbenchmark. The table holds 1 billion rows with timestamp_ms drawn uniformly from 30 days (1 to 31 January 2026, 2,592,000,000 ms), about 0.386 rows per millisecond, in random order. Every partition of 8,192 rows therefore spans almost the whole month, and min/max prunes nothing. All waste is on timestamp_ms. Each query picks a random start x. ClickBench. 15 of the 43 queries have wasted reads under min/max. In total, these are 58,742 wasted reads. Most come from four LIKE '%google%' queries (Q20–Q23) and from the second scan of the ORDER BY … LIMIT 10 queries Q23 and Q24. That scan fetches the 10 result rows by row id, and DuckDB 1.4.4 never prunes it.

Step 3 · Implement

Statistics placed only where the logs show waste

Statistics are built per partition and checked only after min/max fails to prune. Columns are named at runtime (PRUNING_STATS_COLUMNS="table.column:kind:words"); unlisted columns get nothing and cost nothing. With everything off, the binary returns the same results and the same pruning counts as stock DuckDB. In these runs the statistics are built while the database is attached (ATTACH) and are not stored in the file. The budget is 200 64-bit words (1.6 KB) per partition and column for the sensor data, and 2,000 words (16 KB) for the trigram statistic on ClickBench.

Occupancy numbers, dates

Splits the value range into equal-width cells and stores which cells are occupied, Golomb-coded. Keeps value order, so it answers points, IN lists and ranges.

Nullspace points

Hashes values into buckets and stores vectors that every present value satisfies over GF(2) or GF(3). Close to the information-theoretic minimum for membership; answers points and IN lists, not ranges.

Trigram LIKE on strings

Per partition, the set of distinct 3-byte substrings of a string column, encoded with the nullspace codec. URL LIKE '%google%' can only match if every trigram of the pattern occurs in the partition:

goooogoglgle

If any one is provably absent, the partition is skipped. It cannot prune NOT LIKE.

Predicate cache repeated predicates

After Schmidt et al. (SIGMOD 2024). For every scan, the cache remembers per partition whether any row passed the scan's whole filter conjunction (2 bits per partition). The next query with the same filters skips the partitions known to be empty. The cache starts empty. It records a partition only once that partition is fully decided, and any write to the table clears it.

Row-id range check engine fix

ORDER BY … LIMIT 10 queries find the 10 winning row ids, then scan the table again with rowid IN (…). DuckDB 1.4.4 checks that filter against row-id statistics that are always empty, so it opens every partition. The fix compares the filter with each partition's known row-id range. It needs no stored data and costs nothing to build. DuckDB v2.0.0 (October 2026) ships the same check at row-group level (RowGroup::CheckRowIdFilter), so the gap exists only in v1.4.4 through v1.5.6. On v2.0.0, these 24,398 wasted reads are pruned by stock DuckDB.

Related work

Per-partition min/max goes back to Small Materialized Aggregates (Moerkotte, VLDB 1998) and is refined in Data Blocks (Lang et al., SIGMOD 2016). Workload-driven skipping appears in fine-grained and skipping-oriented partitioning (Sun et al., SIGMOD 2014; PVLDB 2016) and adaptive data skipping (Qin and Idreos, SIGMOD 2016). Occupancy is closest to Column Imprints (Sidirourgos and Kersten, SIGMOD 2013), which keep a bitmap of histogram bins per cache line, and to range filters such as SuRF (SIGMOD 2018), Rosetta (SIGMOD 2020), Proteus (SIGMOD 2022) and Grafite (SIGMOD 2024). Its Golomb coding follows Putze et al. (WEA 2007). Nullspace builds on retrieval-based membership structures over GF(2): Dietzfelbinger and Pagh (ICALP 2008), XOR filters (Graf and Lemire, JEA 2020) and Ribbon filters (Dillinger and Walzer, 2021). N-gram pruning for LIKE dates to multigram indexes (Cho and Rajagopalan, ICDE 2002). ClickHouse ships per-granule n-gram Bloom filters as skipping indexes (Schulze et al., PVLDB 2024). The predicate cache follows Schmidt et al. (SIGMOD 2024) and shares the side-effect-of-queries idea with database cracking (Idreos et al., CIDR 2007). Snowflake reports LIMIT and top-k pruning in production (Zimmerer et al., 2025). On the tuning side, this work continues automated physical design, from AutoAdmin (Chaudhuri and Narasayya, VLDB 1997) to Azure SQL auto-indexing (Das et al., SIGMOD 2019) and LLM-based tuners such as GPTuner (PVLDB 2024) and λ-Tune (SIGMOD 2025).

Why the predicate cache alone does not reach zero

With the predicate cache as the only strategy, the repeat pass still leaves 24,398 wasted reads. All of them are in the fetch scans of Q23 and Q24 (12,200 and 12,198); every other scan, including the search scans of Q23 and Q24, drops to 0. The fetch scan has no filter of its own. Its filters, rowid IN (10 ids), rowid >= a and rowid <= b, are built at run time by the semi-join that DuckDB uses for late materialization. The cache key is made only from a scan's static filters, so the fetch scan has no key, and the log reports it as not cacheable (no_static_filters). A key made from the 10 ids would only help an identical rerun on unchanged data. The row-id check needs no key. It compares the ids with each partition's row-id range and prunes 12,200 and 12,198 partitions on the first run, with nothing stored. The two strategies cover different scans, so only together do they reach 0.

Why the predicate cache already prunes on the first run

The cache key is the table plus the filters pushed into the scan. The selected columns, GROUP BY and ORDER BY do not matter. Within the first pass, a query is the first to see its filter only if no earlier query used it:

  • Q11 has the same filter as Q10 (MobilePhoneModel <> ''), which ran just before. Q10 reads its 14 empty partitions and records them, and Q11 skips them.
  • Q13, Q14, Q30, Q31 reuse Q12's SearchPhrase <> '' and skip its 72 empty partitions.
  • Q23 reuses Q20's URL LIKE '%google%' and skips the 1,107 empty partitions that its top-N threshold did not already prune. Q24 and Q26 reuse SearchPhrase <> '' in the same way (6 and 7 partitions).

What each strategy covers

  • Trigrams help only Q20–Q23 (LIKE), on the first run, with nothing learned in advance.
  • The predicate cache prunes every empty partition of a repeated filter, including multi-column conjunctions and NOT LIKE. It does nothing for a filter seen for the first time, and nothing for the dynamic row-id filter.
  • The row-id check removes almost all waste in the second scan of Q23 and Q24 (12,200 and 12,198 partitions).
  • Combined, the first run leaves 13,725 wasted reads. Once every filter has been seen, none are left.
